  1. ¿Por qué settings.py (Pydantic Settings) en lugar de os.getenv?

  Usar Pydantic Settings (settings.py) es el estándar de oro en proyectos modernos de Python (FastAPI/Django) por varias razones críticas:

   * Validación Temprana (Fail-Fast): Con os.getenv, si olvidas una variable, el código fallará mucho después, quizás en mitad de una llamada a la API.
     Pydantic valida al arrancar la aplicación: si falta algo crítico o tiene un tipo incorrecto (ej: esperas un int y llega un str), la app ni siquiera
     sube, lo que ahorra horas de debugging.
   * Centralización: Tienes un único lugar para ver todas las configuraciones del sistema. No tienes que buscar por todo el código dónde se llamó a
     os.getenv.
   * Tipado (IntelliSense): Al usar settings.github_token, tu editor (VS Code/Cursor) sabe que es un string y te da autocompletado. Con
     os.getenv("GITHUB_TOKEN"), el editor no sabe qué es.
   * Gestión de Entornos: Pydantic permite cargar automáticamente diferentes archivos .env (como tu .env.develop) de forma transparente según la
     configuración.

    1 # 3. Nodos del Grafo
    2 async def call_model(state: AgentState, config):
    3     # ... razonamiento del LLM ...
    4     response = await llm.ainvoke(messages, config)
    5     return {"messages": [response]}
    6
    7 def should_continue(state: AgentState) -> Literal["tools", END]:
    8     last_message = state["messages"][-1]
    9     # SI HAY TOOL_CALLS -> SIGUE A TOOLS (ACT)
   10     if last_message.tool_calls:
   11         return "tools"
   12     # SI NO -> TERMINA (REASONING FINAL)
   13     return END
   14
   15 # 4. Configurar el flujo (ReAct loop)
   16 workflow = StateGraph(AgentState)
   17 workflow.add_node("agent", call_model) # REASONING
   18 workflow.add_node("tools", tool_node)  # ACTING
   19
   20 workflow.add_edge(START, "agent")
   21 workflow.add_conditional_edges("agent", should_continue) # EL CEREBRO DEL REACT
   22 workflow.add_edge("tools", "agent") # VUELVE A RAZONAR TRAS ACTUAR

  ¿Por qué esto es ReAct?
  El patrón ReAct (Reasoning + Acting) se basa en un bucle:
   1. Reasoning: El nodo agent recibe la consulta y decide si necesita información externa (genera una tool_call).
   2. Acting: Si el should_continue ve una tool_call, envía el flujo al nodo tools.
   3. Observation: Las herramientas se ejecutan y el resultado vuelve al agent.
   4. Final Reasoning: El agent observa el resultado de la herramienta y decide si ya tiene la respuesta final para el usuario o
      si necesita "actuar" de nuevo.

  Si ves en tu log de consola esto:

   1 19:48:21 [INFO] ... Enviando mensajes al Grafo...
   2 19:48:24 [INFO] ... Buscando pedidos pendientes... (Acting)
   3 19:48:25 [INFO] ... Respuesta generada... (Final Reasoning)
  Ese "salto" entre el modelo y la herramienta es precisamente el patrón ReAct en acción.

  Dato de optimización: Al usar gpt-4o-mini con bind_tools, el modelo es extremadamente eficiente siguiendo este patrón, lo que
  nos permite mantener los costos bajos mientras el agente "piensa" antes de responder.

  1. ¿Qué tipo de memoria es?
  Lo que acabas de implementar con AsyncPostgresSaver es Memoria a Corto Plazo (Short-Term Memory) pero con persistencia. 

   * Memoria a Corto Plazo (Checkpointing): LangGraph guarda el "estado completo" del grafo en un punto del tiempo (los mensajes, las variables, etc.).
   * Persistencia: Al guardarlo en Supabase en lugar de en la RAM, esa memoria a corto plazo no se borra cuando apagas el servidor. 
   * Memoria a Largo Plazo (Long-Term Memory): Se suele implementar con una base de datos de vectores (como pgvector) para que el agente aprenda datos del
     usuario a través de meses o años (ej: "A este usuario le gustan las ofertas los lunes"). Por ahora, nos enfocamos en que el agente no olvide lo que
     hablamos en esta sesión.

✦ Para ver las "tripas" de la memoria de tu agente en Supabase, lo más interesante no es la tabla de datos binarios (que es ilegible para humanos), sino la
  tabla de metadatos, que es donde LangGraph organiza quién dijo qué y cuándo.

  Sigue estos pasos en tu SQL Editor de Supabase:

  1. Ver el historial de conversaciones activo
  Ejecuta esta consulta para ver qué hilos (thread_id) tienes guardados y cuándo fue su última interacción:

    1 SELECT 
    2     thread_id, 
    3     checkpoint_id, 
    4     parent_checkpoint_id,
    5     type,
    6     metadata->>'step' as paso_del_grafo,
    7     metadata->>'source' as origen,
    8     CAST(metadata->>'ts' AS TIMESTAMP) as fecha_interaccion
    9 FROM checkpoint_metadata
   10 ORDER BY fecha_interaccion DESC;

  2. ¿Qué significan estos datos?
   * thread_id: Es el identificador único de la conversación (tu session_id). Si hablas con el agente desde dos dispositivos distintos con el mismo ID, verán
     lo mismo.
   * checkpoint_id: Es como una "foto" del cerebro del agente en un momento exacto. Cada vez que el agente da un paso (ej: del nodo agent al nodo tools), se
     crea un nuevo checkpoint.
   * metadata: Aquí LangGraph guarda el "contexto" de la foto. Verás campos como el paso actual del grafo o si el agente estaba esperando una herramienta.

  3. Ver el estado "crudo" de los mensajes
  Si quieres ver los datos reales que el agente está recordando (aunque están serializados), puedes mirar la tabla de checkpoints:

   1 SELECT 
   2     thread_id, 
   3     checkpoint_id, 
   4     octet_length(checkpoint) as tamaño_memoria_bytes
   5 FROM checkpoints
   6 WHERE thread_id = 'tu-session-id-aqui'; -- Reemplaza con tu ID de prueba

  4. Por qué esta memoria es "mejor" (Nivel Senior)
   * Resiliencia Total: Si tu base de datos crece, puedes usar técnicas de Time-Travel. LangGraph permite "retroceder" el agente a un checkpoint_id anterior
     si cometió un error, simplemente cargando esa versión de la memoria.
   * Escalabilidad: Al no estar en la RAM, puedes tener millones de usuarios hablando a la vez. Cloud Run solo cargará la memoria del usuario que esté
     escribiendo en ese microsegundo, ahorrando costos de infraestructura masivamente.
   * Auditoría: Ahora tienes un log real de lo que el agente "pensó" antes de responder, lo cual es oro puro para depurar errores de lógica en el futuro.

✦ Como ingeniero senior experto en sistemas agénticos, te confirmo que lo que buscas es un patrón llamado RAG (Retrieval-Augmented Generation) integrado como
  una Herramienta (Tool) dentro de tu grafo de LangGraph.

  Los ingenieros expertos no simplemente "leen el PDF" en cada consulta (sería lento y costoso en tokens); lo que hacemos es crear una Base de Datos
  Vectorial. Aquí te explico la arquitectura de nivel Staff Engineer que deberías implementar:

  1. El Patrón "RAG as a Tool"
  En lugar de pasarle todo el PDF al modelo en el prompt, creamos una herramienta (ej: search_cheese_catalog) que el agente decide usar solo cuando el
  usuario pregunta por detalles técnicos de quesos que no están en Shopify.

  2. Arquitectura Técnica (El Stack Experto)
  Dado que ya usas Supabase, la decisión de arquitectura más inteligente es usar pgvector (una extensión de Postgres que ya tienes disponible en Supabase).

  El flujo es el siguiente:
   1. Ingesta (Una sola vez): Se lee el PDF, se divide en trozos pequeños (chunks) y se convierten en vectores (embeddings) usando un modelo de OpenAI
      (text-embedding-3-small).
   2. Almacenamiento: Estos vectores se guardan en una tabla nueva en tu base de datos de Supabase.
   3. Recuperación (Retrieval): Cuando el agente usa la herramienta, esta convierte la pregunta del usuario en un vector, busca los trozos más parecidos en
      Supabase y le devuelve al agente solo la información relevante.
