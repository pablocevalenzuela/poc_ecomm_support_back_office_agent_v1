  1. ¿Por qué settings.py (Pydantic Settings) en lugar de os.getenv?

  Usar Pydantic Settings (settings.py) es el estándar de oro en proyectos modernos de Python (FastAPI/Django) por varias razones críticas:

   * Validación Temprana (Fail-Fast): Con os.getenv, si olvidas una variable, el código fallará mucho después, quizás en mitad de una llamada a la API.
     Pydantic valida al arrancar la aplicación: si falta algo crítico o tiene un tipo incorrecto (ej: esperas un int y llega un str), la app ni siquiera
     sube, lo que ahorra horas de debugging.
   * Centralización: Tienes un único lugar para ver todas las configuraciones del sistema. No tienes que buscar por todo el código dónde se llamó a
     os.getenv.
   * Tipado (IntelliSense): Al usar settings.github_token, tu editor (VS Code/Cursor) sabe que es un string y te da autocompletado. Con
     os.getenv("GITHUB_TOKEN"), el editor no sabe qué es.
   * Gestión de Entornos: Pydantic permite cargar automáticamente diferentes archivos .env (como tu .env.develop) de forma transparente según la
     configuración.

    1 # 3. Nodos del Grafo
    2 async def call_model(state: AgentState, config):
    3     # ... razonamiento del LLM ...
    4     response = await llm.ainvoke(messages, config)
    5     return {"messages": [response]}
    6
    7 def should_continue(state: AgentState) -> Literal["tools", END]:
    8     last_message = state["messages"][-1]
    9     # SI HAY TOOL_CALLS -> SIGUE A TOOLS (ACT)
   10     if last_message.tool_calls:
   11         return "tools"
   12     # SI NO -> TERMINA (REASONING FINAL)
   13     return END
   14
   15 # 4. Configurar el flujo (ReAct loop)
   16 workflow = StateGraph(AgentState)
   17 workflow.add_node("agent", call_model) # REASONING
   18 workflow.add_node("tools", tool_node)  # ACTING
   19
   20 workflow.add_edge(START, "agent")
   21 workflow.add_conditional_edges("agent", should_continue) # EL CEREBRO DEL REACT
   22 workflow.add_edge("tools", "agent") # VUELVE A RAZONAR TRAS ACTUAR

  ¿Por qué esto es ReAct?
  El patrón ReAct (Reasoning + Acting) se basa en un bucle:
   1. Reasoning: El nodo agent recibe la consulta y decide si necesita información externa (genera una tool_call).
   2. Acting: Si el should_continue ve una tool_call, envía el flujo al nodo tools.
   3. Observation: Las herramientas se ejecutan y el resultado vuelve al agent.
   4. Final Reasoning: El agent observa el resultado de la herramienta y decide si ya tiene la respuesta final para el usuario o
      si necesita "actuar" de nuevo.

  Si ves en tu log de consola esto:

   1 19:48:21 [INFO] ... Enviando mensajes al Grafo...
   2 19:48:24 [INFO] ... Buscando pedidos pendientes... (Acting)
   3 19:48:25 [INFO] ... Respuesta generada... (Final Reasoning)
  Ese "salto" entre el modelo y la herramienta es precisamente el patrón ReAct en acción.

  Dato de optimización: Al usar gpt-4o-mini con bind_tools, el modelo es extremadamente eficiente siguiendo este patrón, lo que
  nos permite mantener los costos bajos mientras el agente "piensa" antes de responder.
